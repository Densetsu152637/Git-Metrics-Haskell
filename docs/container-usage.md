# Compose-first container usage

Use the consuming project's Compose configuration as the source of truth for services, build context, dependencies, networks, volumes, environment, and profiles. Before suggesting or running container commands, inspect the repository's `compose.yaml`, `compose.yml`, `docker-compose.yaml` or `docker-compose.yml`, override files, Dockerfiles, scripts, Makefiles, and relevant READMEs. Determine the actual service names with `docker compose config --services` using that project's configuration. Do not present guessed service names as executable defaults.

Use the modern `docker compose` CLI. Use a legacy `docker-compose` wrapper only when the project explicitly documents it or requires it. Preserve the same ordered `-f` file list, applicable `--env-file`, profiles, project name, and project directory for every lifecycle command; these settings determine the Compose model and project identity. Discover existing wrapper scripts and prefer them when they encode those project-specific arguments.

For Compose-managed services:

- Reuse already-running services. Enter a running service with `docker compose ... exec -T SERVICE COMMAND` for scripts and CI (omit `-T` for an interactive terminal). `exec` targets a running container; it does not create a fresh environment.
- Run an intentional one-off command with `docker compose ... run --rm SERVICE COMMAND`. It creates a new service container; service ports are not published unless requested, and dependencies may be started. Inspect the service configuration and command before use.
- Build and start selected services when needed with `docker compose ... up -d --build SERVICE...`. For ordinary startup, use `up -d SERVICE...`; rebuild only when relevant build inputs changed or the task requires it. Include required dependencies according to the Compose model.
- Build without starting containers using `docker compose ... build SERVICE...` when a build-only step is required. This remains Compose-managed and respects the service's configured build context and arguments.
- Match the update method to where the changed files enter the container. Bind-mounted source may become visible without rebuilding; code copied into an image requires a rebuild and container recreation through `up --build`. `build` alone does not update an already-running container, and `restart` does not apply changed Compose configuration or environment. Check the project's mount and image configuration before deciding.
- Use standalone `docker build` or `docker run` for a Compose-managed service only when the task has an explicit reason, such as diagnosing a minimal isolated reproduction. State the reason and how the command preserves required build arguments, mounts, networking, and environment.

The `...` above denotes the project's resolved, identical Compose options, not literal syntax. Replace `SERVICE`, `COMMAND`, and service lists only with names and commands discovered in the project. Examples of options to carry consistently are `-f <compose-file>`, any additional `-f <override-file>` in order, `--env-file <env-file>`, `--profile <profile>`, `-p <project-name>`, and `--project-directory <directory>`. Omit only options that the project does not use; do not silently switch project identity or configuration between build, start, exec, logs, and cleanup.

Check startup readiness using the project's documented readiness check. `docker compose up --wait` waits for services to be running or healthy; a service is only reported healthy when a healthcheck exists. Without a meaningful healthcheck, confirm application readiness using its documented endpoint, probe, or logs before running dependent checks.

For status and diagnosis, use the same Compose options with `ps`, `logs --tail <count> SERVICE`, and `config --services`. See [validation](validation.md) for a repeatable sequence and [environment configuration](environment-configuration.md) for safe handling of variables and credentials.

Stop only the services or project in scope. Prefer `docker compose ... stop SERVICE...` when preserving containers and networks matters. `docker compose ... down` removes project containers and networks; do not add `-v` or remove images unless the task explicitly calls for those resources and their ownership/data implications have been checked. Do not use global prune commands as routine cleanup.
